# Design Workspace Framework — Workspace Protocol

Protocol version: 031

## Purpose

This file is the versioned **Workspace Protocol** for the **Design Workspace Framework**. It defines the current operational rules for working with a concrete Design Workspace and may evolve as the framework improves.

The **Design Workspace Framework** is the reusable abstract methodology for organizing long-running design work: knowledge ownership, Design Sessions, product and technical decisions, PRD/SPEC production, checkpoints/parking, roadmap selection, temporary implementation slices, integrity validation, versioning, workspace snapshotting, and design packaging.

The surrounding project-level chat protocol may provide broad philosophy. **This Workspace Protocol wins for concrete Design Workspace procedure.**

A Design Workspace follows a single-owner principle: each kind of knowledge has one canonical owning file. Other files may provide brief navigation summaries or historical provenance, but they must not become competing sources of truth.

## Framework Vocabulary

Use these terms consistently when discussing the framework itself versus one project using it:

- **Design Workspace Framework** — the abstract reusable methodology/system defined conceptually by these operating conventions. It is not one project's ZIP or file tree.
- **Workspace Protocol** — the formal, versioned operating rules for the Design Workspace Framework as instantiated by `WORKSPACE-PROTOCOL.md`.
- **Design Workspace** — one concrete project instance of the framework, including its canonical files and mutable design state.
- **Workspace Revision** — one versioned canonical state of a Design Workspace, identified by `Workspace version: NNN`.
- **Workspace ZIP / Workspace Snapshot** — the complete versioned ZIP transport of one Design Workspace Revision. **Workspace ZIP** is the normal user-facing term; **Workspace Snapshot** remains the formal framework synonym. The latest complete workspace ZIP explicitly supplied by the user is the canonical source for the current chat.
- **Extracted Working Copy** — the local unzipped workspace used during the current chat. It is mutable working state only until a persistence command produces and returns the next complete versioned Workspace ZIP.
- **Design Package** — a deterministic structured ZIP of the nine design artifacts defined by the `Package` command. It is a compact shareable design projection, not a recoverable Design Workspace and not the Portable Implementation Package.
- **Portable Implementation Handoff** — when a project has an accepted implementation-handoff contract, the overall capability for transferring prepared design/Delivery truth to an implementation executor. It is distinct from the Design Package command.
- **Portable Implementation Package / Implementation Package** — the concrete project-specific artifact that realizes a Portable Implementation Handoff. Its accepted project contract may include Delivery material, Concepts, and other implementation context beyond the fixed nine-file Design Package; it is not created by silently changing the Design Package membership.
- **Design Session** — one bounded conceptual design unit within a Design Workspace; it may span multiple Chat Segments.
- **Design Pace** — chat-local interaction policy for an active Design Session: `NORMAL` or `FAST`.
- **Frontier Wave Traversal** — FAST's bounded breadth-first mechanism for processing the current conceptual branch in waves; detailed method is owned by `skills/frontier-wave-traversal.md`.
- **Collaboration Profile** — mandatory workspace-local communication calibration stored in `project-context/COLLABORATION.md`; it guides explanation/interaction style but never owns product or technical truth.
- **Modular Workspace Skill** — a directory-scoped reusable Agent Skill under `skills/<skill-name>/SKILL.md`, with optional `references/`, `scripts/`, `assets/`, and eval resources loaded only when the skill is invoked.
- **Mini-Course Source Package** — a ready-to-build source ZIP generated by the `MiniCourse` capability. It is a derived explanatory artifact, not product/design authority; its `course-brief.json` records the source revision/context used to generate it when available.
- **Developer Concept** — a derived, non-authoritative deep-dive under `concepts/` that reorganizes several canonical decisions/contracts into one subsystem mental model for implementation, debugging, or review.

Do not use **Workspace Protocol** as a synonym for the whole Design Workspace Framework. Likewise, do not use **Design Workspace** to mean the abstract reusable framework when referring to rules that could apply to many projects.

## Operating Modes

The workspace supports two explicit operating modes.

### Design Session Mode

Use when discussing or deciding synchronization behavior, product requirements, architecture, or implementation direction.

- Focus on one conceptual decision area.
- A conceptual **Design Session** may span multiple AI chats when needed; each AI conversation used for that Design Session is a **Chat Segment**.
- Use the selected session file as the discussion workspace across all Chat Segments.
- Accepted product/behavior decisions may be added or explicitly reopened in `design/decisions.md` as `D-*`.
- Accepted implementation/architecture decisions belong in `design/technical-decisions.md` as `TD-*`; a bounded temporary implementation slice may use explicitly approved `PROVISIONAL` TDs under the temporary-spec exception defined below.
- Classify by observable behavior: if the implementation mechanism could change without changing observable PRD behavior, it normally belongs in `design/technical-decisions.md`; otherwise it normally belongs in `design/decisions.md`.
- A Technical Decision never overrides a Product Decision or PRD requirement.
- A chat boundary never forces a new Design Session.

### Design Pace

Every chat-local Design Session selection uses one explicit **Design Pace**:

- **NORMAL** — the careful interaction policy: one important question at a time, explicit user acceptance for `D-*` / `TD-*`, and new branches deferred under the normal Branching Rule.
- **FAST** — an accelerated interaction policy for active design decision-making only. FAST uses **Frontier Wave Traversal** to process the current conceptual branch in bounded breadth-first waves, with limited delegated authority for qualifying low-risk decisions.

Design Pace is orthogonal to Operating Mode. It applies only while discussing/deciding inside Design Session Mode and never changes Maintenance / Audit Mode disposition. FAST does **not** accelerate or weaken Workspace Orientation, checkpoint/park persistence, finalization mechanics, integrity validation, normalization, versioning, workspace snapshotting, or design-package export.

Design Pace is **chat-local and non-persistent**. When a Design Session is explicitly initialized or resumed and the user has not already specified `NORMAL` or `FAST`, ask which pace to use before the first substantive design question. `Continue` inherits the pace already selected for the current chat-selected Design Session. A user may switch pace mid-session with an explicit natural-language instruction such as `Fast`, `Fast on`, `Normal`, or `Fast off`.

Selecting FAST is explicit bounded delegation for the `AUTO` classification defined by `skills/frontier-wave-traversal.md`; it is not blanket authority to create arbitrary product or technical decisions.

### Maintenance / Audit Mode

Use when the user explicitly asks to inspect, clean up, reorganize, verify, or improve the workspace/protocol/accumulated knowledge itself.

Maintenance / Audit Mode always has one explicit **disposition submode**:

- **Standard Mode** — preserve the iterative design workflow. Genuine unresolved product/design decisions that require decision-making authority are prepared as future focused design sessions rather than silently guessed.
- **Handoff Mode** — preserve the same audit rigor, but do not create/prepare future design sessions for genuine unresolved product/design decisions. Route those findings into `design/OPEN-DECISIONS.md` as stable `OD-NNN` handoff decisions for the implementation owner.

If a request enters Maintenance / Audit Mode but does **not** specify Standard or Handoff Mode, ask the user which mode they want **before performing the substantive audit/maintenance work**. Do not assume a default, even if the user is in a hurry. Natural-language instructions such as “delegate unresolved decisions to the developer” clearly select Handoff Mode; instructions such as “prepare follow-up design sessions for anything unresolved” clearly select Standard Mode.

Both submodes share the same detection and repair rigor:

- Do not automatically advance the next product-design session.
- Do not reopen or change accepted product/design decisions unless the user explicitly requests it or a genuine contradiction requires it.
- Prefer semantic-preserving changes: ownership cleanup, deduplication, stale-status repair, link repair, protocol clarification, and integrity checks.
- Inspect whichever workspace files are relevant to the audit rather than treating an open design session as active by default.
- Deterministic/documentary defects whose correct answer is already established by canonical truth are fixed/reported according to `Maintain` versus `Audit`; they do not become sessions or Open Decisions.
- Ordinary technical implementation freedom already delegated to technical design is not an Open Decision merely because the exact implementation has not been selected; when such a mechanism is actually decided, record it in `design/technical-decisions.md` rather than hiding it only inside SPEC prose.
- Accepted limitations/known safe rough edges are documented as such rather than being promoted to Open Decisions without a genuine missing decision.

## Command Contract

The following terms have explicit workspace meanings. Treat them case-insensitively and honor them when they appear either alone or inside a natural-language request. An explicit command meaning wins over a broader inference from the surrounding request.

### `Unzip`

Extract a supplied ZIP and identify whether it is a **Workspace Snapshot / Workspace ZIP** or a **Design Package** before assigning workspace semantics.

- A Workspace ZIP is the complete canonical transport for one Workspace Revision and may support Orientation, session work, mutation, checkpointing, finalization, and future reseeding.
- A Design Package contains only the shareable design products. It may be reviewed as a deliverable, but it is **not** a Design Workspace and cannot by itself support Workspace Orientation, session recovery, mutation, or reseeding.

Extraction alone does not authorize edits, auditing, normalization, version changes, or design work.

### `Read` / `Orient`

Perform **Workspace Orientation** without selecting or starting a Design Session. Natural requests such as `read the workspace`, `orient yourself`, or `Unzip and read` use this behavior unless another operation is also explicit.

For a supplied Workspace ZIP:

1. Unzip it locally and confirm it contains a complete workspace root.
2. Read `README.md`, `WORKSPACE-PROTOCOL.md`, **mandatory** `project-context/RULES.md`, and **mandatory** `project-context/COLLABORATION.md`.
3. Verify that README workspace/protocol versions agree with the protocol and that required canonical files are present.
4. Read enough canonical current-state files to understand the workspace safely.
5. Determine session eligibility from each open session's durable status and Activation Gate.
6. Present the next-work candidates using **Session Selection Priority** below.
7. Do **not** select, activate, resume, or mutate a Design Session automatically. Ask the user what they want to work on next.

Workspace Orientation is read-only unless another explicit command authorizes changes. The supplied Workspace ZIP remains the canonical starting revision; the extracted directory is only the current chat's working copy until a persistence command returns the next complete ZIP.

### `Initialize`

Enter **Design Session Mode** only after a session is explicitly selected.

1. If the user names a session, validate its Activation Gate, read the normal Start files for that Design Session, and make it the current **chat-local session selection**.
2. If the user does not name a session, perform Workspace Orientation and present the ranked candidates; do not choose one automatically.
3. Establish the selected session's already-settled product boundaries from `design/decisions.md` / `output/agent/PRD.md`; for a technical-design session, also read `design/technical-decisions.md` and the relevant current `output/agent/SPEC.md` material before proposing implementation choices.
4. Resolve the chat-local **Design Pace** before substantive design discussion unless the user already specified it. Accept combined forms such as `Initialize Session 020 Fast`; otherwise ask `NORMAL or FAST?`.
5. Begin according to the selected pace: NORMAL starts with the next important unresolved question; FAST starts by identifying the current branch's visible leaves and following `skills/frontier-wave-traversal.md`.

Starting a session does not itself rewrite durable session status or increment the workspace version. `ACTIVE` and Design Pace are deliberately **not** persisted; both describe only the current chat interaction.

### `Resume`

Explicitly continue an incomplete Design Session that has a durable continuation state.

1. `Resume <session>` explicitly selects that `CHECKPOINTED` or `PARKED` session, subject to its Activation Gate.
2. Bare `Resume` in a fresh chat presents resumable `CHECKPOINTED` sessions first and `PARKED` sessions second, then asks the user to select one; do not auto-select.
3. Read the selected session's **Continuation Snapshot** first, then the referenced accepted decisions/context needed to re-establish the boundary.
4. Resolve the chat-local **Design Pace** unless the user already specified it. Accept combined forms such as `Resume Session 013 Fast`; otherwise ask `NORMAL or FAST?`.
5. Continue from the recorded resume point according to the selected pace. FAST may reconstruct the current branch frontier from the continuation state but must not reinterpret already-settled truth.

If no resumable session exists, say so rather than guessing. Selecting a previously `PARKED` session does not by itself rewrite its durable state; a later `Checkpoint`, `Park`, or `Finalize` persists the resulting lifecycle transition.

### `Continue`

Continue brainstorming the session already selected in the **current chat**, inheriting its current Design Pace. If no current chat selection exists, perform Workspace Orientation and ask the user to choose; do not infer a session merely because a checkpoint exists. If a session is selected but its pace has not yet been resolved, ask `NORMAL or FAST?` before substantive design work. Do not perform maintenance implicitly.

### `Checkpoint`

Persist a resumable handoff for the currently selected Design Session **without completing it** and mark its durable state `CHECKPOINTED`. A checkpoint is created **only when the user explicitly requests one**. Never create a checkpoint merely because the chat is long, the context window is growing, a convenient stopping point was reached, or the agent believes a handoff would be useful.

Follow **Checkpoint or Park a Design Session** below, then create and return the resulting complete versioned Workspace ZIP. The ZIP is the persisted handoff.

### `Park`

Persist a resumable handoff for the currently selected incomplete Design Session and mark it `PARKED`, meaning the work is intentionally deferred from the normal near-term roadmap. `Park` preserves the same session and Continuation Snapshot; it does not complete the session or create a `part-2` file.

Use `PARKED` when a session was intentionally entered out of roadmap order (for example, for a bounded Temporary Implementation Slice) or when the user explicitly wants incomplete work preserved but deprioritized.

Follow **Checkpoint or Park a Design Session** below, then create and return the resulting complete versioned Workspace ZIP. The ZIP is the persisted handoff.

### `Finalize`

Persist only conclusions that were settled during the current design discussion. In NORMAL, `D-*` / `TD-*` conclusions require explicit user acceptance. In FAST, a surfaced `AUTO` conclusion that qualified under the bounded delegation rules and was not overridden before finalization also counts as settled. Update the current chat-selected session, canonical ledgers/outputs/navigation, and session status as required by **Finish a Design Session**. Validate the complete local workspace, create the next deterministic versioned Workspace ZIP, and return it to the user as the finalized canonical revision. Do not invent agreement for unresolved questions, `PACKET` leaves, `DEFER` leaves, or unresolved `BRAKE` leaves.

### `Audit`

Enter **Maintenance / Audit Mode** and inspect the requested scope for inconsistencies, stale state, broken references, duplication, protocol violations, or similar problems. The request must resolve **Standard Mode** versus **Handoff Mode** first; if the user says only `Audit`/“audit” without selecting a submode, ask which one they want before auditing.

**Audit remains report-only by default.** Do not modify canonical files unless the user also asks to fix/apply them. In Standard Mode, report genuine unresolved design findings together with prepared follow-up-session proposals. In Handoff Mode, report them as proposed `OD-NNN` records using the `design/OPEN-DECISIONS.md` schema; persist those records only when write/apply permission is also present.

### `Maintain`

Enter **Maintenance / Audit Mode**, audit the requested scope, and apply justified semantic-preserving repairs. The request must resolve **Standard Mode** versus **Handoff Mode** first; if the user says only `Maintain`, `Maintenance`, or an equivalent maintenance request without selecting a submode, ask which one they want before maintaining.

Do not intentionally change accepted product/design behavior. In Standard Mode, genuine unresolved design/product decisions that require decision-making authority are prepared as future focused sessions. In Handoff Mode, those same findings are written to `design/OPEN-DECISIONS.md` instead of creating/preparing future design sessions. If canonical files change, follow **Finish Maintenance / Audit Work**.

### `MiniCourse`

Create a short, self-guided interactive technical mini-course from current authoritative source material **without selecting or activating a Design Session**. This is an explanatory-projection capability, not a design-decision workflow. The owning modular skill is `skills/creating-interactive-technical-courses/SKILL.md`.

`MiniCourse` is read-only with respect to canonical design truth. It must not modify `design/decisions.md`, `design/technical-decisions.md`, PRD, SPEC, edge cases, session status, Open Questions, or Open Decisions merely to make the course easier to teach. Unsupported or unresolved behavior remains unsupported/unresolved in the course.

#### Preparation

Before generation, resolve these five dimensions. Values already supplied by the command/request count as resolved and must not be re-asked:

1. **Time budget** — hard required-path maximum; the capability ceiling is 14 days, with normal use expected to be hours or a few days.
2. **Audience / prior knowledge** — who will take it and what technical/domain knowledge may be assumed.
3. **Desired capabilities / depth** — what learners should be able to explain, predict, review, debug, or implement afterward.
4. **Scope** — whole subject or bounded area, including emphasis and exclusions.
5. **Delivery / persistence** — default downloadable source ZIP only; `--save` also persists the same ZIP into the workspace.

Ask unresolved preparation dimensions together in one compact turn when practical. After they are resolved, perform one ambiguity scan and ask at most **5 additional targeted questions total**. Ask those only when ambiguity materially affects correctness, scope, prerequisites, course structure, or desired outcomes; resolve lower-impact ambiguity with professional judgment.

Natural command arguments may pre-resolve fields, for example:

- `MiniCourse 2h`
- `MiniCourse 90m --scope Recovery --depth implementation-ready`
- `MiniCourse 1 day --audience new backend developer --save`

Argument syntax is intentionally lightweight; interpret values as natural language rather than requiring shell-perfect quoting.

#### Default Design Workspace source set

For a course about the current Design Workspace, begin from the valid committed Workspace Revision and use:

- **primary teaching truth:** `output/human/PRD.md`, `output/human/SPEC.md`, `output/edge-cases.md`;
- **supporting context/terminology:** `project-context/RULES.md`, `project-context/context.md`, `project-context/GLOSSARY.md`;
- **selective precision/rationale:** `output/agent/PRD.md`, `output/agent/SPEC.md`, `design/decisions.md`, and `design/technical-decisions.md` only where the human projections do not provide enough supported explanation;
- **unresolved-truth check:** inspect `design/OPEN-QUESTIONS.md` and `design/OPEN-DECISIONS.md` so unresolved material is not taught as settled;
- historical `sessions/` only when specific provenance is genuinely needed.

A narrower `--scope` should reduce what is read/taught proportionally rather than forcing a complete workspace digest.

#### Generation and deliverable

Follow `skills/creating-interactive-technical-courses/SKILL.md`. The default deliverable is one **ready-to-build source ZIP**, not a compiled HTML file. The ZIP must contain the complete course source, `course-brief.json`, a concise `README.md`, and package scripts such that on a developer machine:

```bash
npm install
npm run build
```

produces and verifies one self-contained offline HTML file under `dist-release/`. The generated ZIP excludes `node_modules/`, compiled output, caches, and VCS/editor junk. Do not require npm registry/network access inside the chat/agent runtime merely to generate the course source ZIP.

#### `--save`

Without `--save`, do not modify the Design Workspace; return the ZIP only in the current interaction.

With `--save`, after course generation:

1. retain the source Workspace Revision in `course-brief.json`;
2. persist only the source ZIP under local `artifacts/mini-courses/`, using a collision-resistant filename that includes the course slug and source Workspace Revision;
3. do not persist compiled HTML by default;
4. treat the saved course ZIP as derived non-authoritative workspace content; if this changes the workspace, increment the Workspace Revision and return the next complete Workspace ZIP.

The course remains tied to the recorded source revision.

### `Normalize`

Perform only mechanical/canonicalization cleanup required by **Text and Archive Normalization**: encoding, Unicode normalization, line endings, whitespace, archive root/entry ordering, deterministic metadata, and equivalent non-semantic cleanup. Do not treat `Normalize` as permission for a broad semantic audit or stale-state rewrite.

### `Snapshot`

Create or recreate a deterministic complete **Workspace Snapshot / Workspace ZIP** from the current local workspace revision. This is the canonical transport artifact used to move the workspace between chats.

New workspace ZIPs are named:

```text
workspace-vNNN.zip
workspace-vNNN/
```

A persistence operation that changes canonical contents increments the Workspace Revision before creating the ZIP. Recreating the exact same revision without content changes does not increment the version.

### `Package`

Create or recreate a deterministic **Design Package** from the current Workspace Revision. The ZIP preserves the semantic directory structure and contains **exactly** these nine files:

```text
project-context/RULES.md
project-context/GLOSSARY.md
design/decisions.md
design/technical-decisions.md
output/agent/PRD.md
output/agent/SPEC.md
output/human/PRD.md
output/human/SPEC.md
output/edge-cases.md
```

The Design Package is a compact design-only shareable projection. `RULES.md` is included so a receiving reviewer or implementation stakeholder sees the mandatory project posture. `context.md`, collaboration calibration, open-question/open-decision ledgers, sessions, skills, protocols, temporary artifacts, derived artifacts, and Delivery/Concept material are excluded; the Portable Implementation Package is the separate implementation handoff artifact.

The archive is named `design-package-vNNN.zip`. `Package` is read-only: it does not regenerate, repair, reconcile, or mutate those files, and it does not change workspace/protocol version numbers. If another command in the same request changed canonical contents, persist that new revision as a Workspace ZIP first and package the resulting revision. If any required file is missing, fail rather than silently substituting or expanding the package. If canonical status explicitly marks the Agent PRD/SPEC as stale or incomplete, still package the exact committed files when requested but clearly warn the user that the deliverable reflects that status.

A Design Package is a team-facing design projection, not a recoverable Design Workspace, not the Portable Implementation Package, and not a competing mutable source of truth.

### Combined Commands

When multiple commands are given, execute them **left to right** and preserve each command's boundary. Do not silently widen one command into another.

Examples:

- `Unzip, read` → unpack the workspace, orient to canonical state, present ranked session candidates, and ask the user what to work on; do not auto-select a session.
- `Unzip, normalize, initialize Session 020` → unpack the workspace, perform mechanical normalization only, then explicitly enter Session 020 and begin brainstorming. Do not insert a broad audit between normalization and initialization.
- `Initialize Session 020 Fast` → enter Session 020 with chat-local Design Pace `FAST` and begin with Frontier Wave Traversal rather than asking for pace separately.
- `Resume Session 013 Normal` → resume Session 013 with chat-local Design Pace `NORMAL`.
- `Read, MiniCourse 2h` → orient to the committed workspace, then enter `MiniCourse` preparation/generation without selecting the recommended Design Session.
- `MiniCourse 90m --scope Recovery --save` → generate the time-bounded course ZIP from the relevant canonical source set, then save that ZIP under local `artifacts/mini-courses/` and return a new Workspace ZIP if canonical workspace contents changed.
- Bare `Initialize` after loading a workspace → present the session-selection candidates and wait for explicit selection rather than automatically resuming/starting one.
- `Audit` → ask `Standard or Handoff?` before auditing; after the user selects, inspect and report without fixing unless separately authorized.
- `Audit in Standard Mode` → inspect/report and prepare follow-up-session proposals for genuine unresolved design decisions.
- `Audit in Handoff Mode` → inspect/report and format genuine unresolved design decisions as proposed `OD-NNN` records; persist them only if write/apply permission is also present.
- `Maintain in Standard Mode` → inspect, apply justified maintenance repairs, and prepare future focused sessions for genuine unresolved design decisions.
- `Maintain in Handoff Mode` → inspect, apply justified maintenance repairs, and write genuine unresolved design decisions to `design/OPEN-DECISIONS.md` instead of preparing future sessions.
- `Checkpoint` → persist a resumable `CHECKPOINTED` handoff and return the next complete Workspace ZIP.
- `Park` → persist a resumable `PARKED` handoff and return the next complete Workspace ZIP.
- `Finalize and package` → finalize the Design Session, return the next complete Workspace ZIP, then additionally create the structured nine-file Design Package from that revision.
- `Normalize and snapshot` → mechanically normalize canonical files/archive state, version only if canonical contents changed, then create the Workspace Snapshot.

If the user's natural language clearly expresses one of these operations without using the exact keyword (for example, "start Session 010"), follow the corresponding command semantics. If intent is still genuinely ambiguous, prefer the least-destructive interpretation and do not perform maintenance or canonical rewrites implicitly.

## Workspace ZIP Persistence Discipline

The workspace is persisted as one complete versioned ZIP, not as a mutable external file tree. The user is the custodian of the latest canonical ZIP between chats.

### Persistence boundary

1. Begin from the latest complete Workspace ZIP supplied by the user.
2. Unzip and work locally.
3. Before persistence, validate required files, workspace/protocol versions, links, session/navigation integrity, durable IDs, and any command-specific invariants.
4. Increment the Workspace Revision when canonical contents changed; increment the protocol version only when `WORKSPACE-PROTOCOL.md` changed.
5. Normalize text/archive bytes according to **Text and Archive Normalization**.
6. Create one deterministic complete ZIP under a single version-matching archive root.
7. Verify the generated ZIP can be reopened and matches the local workspace revision.
8. Return the ZIP to the user. That returned complete ZIP is the next canonical revision.

No external mutable workspace, per-file remote identity, transaction marker, `IDLE/WRITING` state, or connector-specific commit protocol is required. If ZIP generation fails, the previously supplied ZIP remains canonical.

## Lifecycle

### Start

1. Require a complete Workspace ZIP for workspace-dependent work; in a fresh chat, ask the user for the latest ZIP if none is supplied.
2. Unzip it locally and validate README/protocol versions and required canonical files.
3. Read `README.md`, this `WORKSPACE-PROTOCOL.md`, **mandatory** `project-context/RULES.md`, and **mandatory** `project-context/COLLABORATION.md` before substantive project reasoning. Treat a missing Collaboration Profile as an invalid workspace bootstrap rather than silently continuing without it. Interpret operational commands using **Command Contract** before doing workspace work.
4. Determine the operating mode from the user's request. `Unzip` + `Read`/`Orient` is **Workspace Orientation**, not Design Session Mode.
5. If the request enters Maintenance / Audit Mode, resolve **Standard** versus **Handoff** before substantive audit work; ask when omitted.
6. Read `project-context/context.md` and `design/decisions.md`; read `project-context/GLOSSARY.md` when stable terminology is relevant; read Open Questions/Open Decisions when relevant.
7. For technical-design/implementation sessions, additionally read `output/agent/PRD.md`, `design/technical-decisions.md`, and relevant `output/agent/SPEC.md` material.
8. In Design Session Mode, read the **explicitly selected** file under `sessions/`; no durable session status automatically selects a current-chat session. Resolve the chat-local Design Pace (`NORMAL` or `FAST`) before substantive design work unless the user already supplied it.
9. In Maintenance / Audit Mode, read all files relevant to the requested audit scope. FAST is unavailable in this operating mode.
10. Treat accepted product and technical decisions as settled unless explicitly reopened; treat `PROVISIONAL` TDs as authorized only within their explicitly scoped temporary implementation specification until canonical SPEC reconciliation.

### Session Lifecycle and Selection

Persisted Design Session status uses exactly these machine-simple values:

- `PLANNED` — prepared future work that has no durable incomplete checkpoint yet.
- `CHECKPOINTED` — incomplete work with a Continuation Snapshot that is intended to remain in the near-term roadmap.
- `PARKED` — incomplete work with a Continuation Snapshot that is intentionally deferred from the normal near-term roadmap but remains explicitly resumable.
- `COMPLETE` — finished historical provenance; never a next-work candidate.

`ACTIVE` is **not** a durable status. The currently discussed session is a **chat-local session selection** that exists only for the current AI conversation. Starting or resuming a session does not require a workspace rewrite merely to say it is active. Until the next persisted lifecycle event, a selected session retains its prior durable state.

Open/prepared session files should expose status near the top. `PLANNED` sessions may use a compact `Session State`; `CHECKPOINTED` and `PARKED` sessions use a `Continuation Snapshot`. Completed historical sessions may retain older completion wording when their completion is already unambiguous.

A session may also declare an optional **Activation Gate**:

```markdown
- Activation gate: NONE
```

or a concise condition/reference such as `Canonical SPEC complete and reviewed`. The session file owns the gate; `README.md` may summarize it for navigation. A gate determines **eligibility**, not priority. If the gate is unsatisfied, do not recommend or start the session unless the user explicitly changes/waives the gate; surface the blocking condition instead.

`PARKED` is not an Activation Gate. A parked session is deliberately lower-priority but may still be explicitly selected when the user wants to resume it or use another authorized temporary implementation escape hatch.

#### Session Selection Priority

When no session is already selected in the current chat, build the navigation list deterministically:

1. eligible `CHECKPOINTED` sessions;
2. eligible `PLANNED` sessions, ordered by the canonical recommended sequence in `README.md`;
3. eligible `PARKED` sessions;
4. gated/ineligible `PLANNED`, `CHECKPOINTED`, or `PARKED` sessions shown separately for awareness, with the unsatisfied gate;
5. `COMPLETE` sessions are historical and excluded from next-work candidates.

Within the same priority class, `README.md` owns explicit roadmap order; if no order exists, use ascending session number only as a deterministic fallback and say that no stronger roadmap preference was recorded.

The ranking is a **recommendation list, not an automatic transition**. Workspace Orientation, bare `Initialize`, bare `Resume`, and `Continue` without a current chat selection must present the relevant candidates and ask the user to select. An explicit `Initialize Session NNN`, `Resume Session NNN`, or equivalent natural-language selection may start that session directly if eligible. Session selection and Design Pace are separate chat-local choices: after selecting a Design Session, resolve `NORMAL` versus `FAST` before substantive design work unless the same user instruction already supplied the pace.

### During a Design Session

- Focus on one conceptual decision area, even when it spans multiple Chat Segments.
- Keep responses concise and conversational. Apply the mandatory `project-context/COLLABORATION.md` workspace-local response calibration unless the user overrides it in the current chat.
- Prefer simple, pragmatic, reversible solutions.
- Separate:
  - confirmed facts,
  - accepted product decisions (`D-*`),
  - accepted/provisional technical decisions (`TD-*`),
  - working assumptions,
  - unresolved questions.
- Under **NORMAL** pace, discuss one important question at a time and follow the ordinary Branching Rule.
- Under **FAST** pace, follow `skills/frontier-wave-traversal.md`: identify the current conceptual branch's visible leaves, classify them `AUTO` / `PACKET` / `DEFER` / `BRAKE`, and process the actionable frontier breadth-first in bounded waves. A Fast Decision Packet may contain at most **5 leaves**.
- FAST may traverse newly exposed descendant leaves only while they remain inside the current conceptual branch. A genuinely different conceptual branch is deferred as future work rather than recursively solved.
- FAST may degrade selectively: an isolated `BRAKE` leaf receives NORMAL-style discussion while unaffected sibling leaves may continue; a root-level or cross-cutting BRAKE pauses frontier advancement until resolved.
- Do not create a `CHECKPOINTED` or `PARKED` continuation state unless the user explicitly asks for that persistence/defer action or an explicitly authorized Temporary Implementation Slice requires the agreed park/checkpoint disposition.

### Checkpoint or Park a Design Session

When the user explicitly asks to persist an incomplete Design Session:

1. Keep the same conceptual Design Session incomplete; do not mark it completed and do not create a `part-2` session file.
2. Update the current chat-selected session file with the reasoning/provenance actually discussed so far.
3. Classify and promote only settled conclusions into the correct canonical ledger:
   - accepted product/observable-behavior conclusions -> `design/decisions.md` as stable `D-NNN`;
   - accepted implementation/architecture conclusions -> `design/technical-decisions.md` as stable `TD-NNN`; use `PROVISIONAL` only when the user explicitly approved the decision for a bounded temporary implementation slice that has not yet been reconciled into the complete architecture.
     In FAST, a surfaced `AUTO` conclusion that met the bounded delegation criteria and was not overridden before persistence counts as settled. `PACKET`, `DEFER`, and unresolved `BRAKE` leaves do not. Unresolved factual questions remain unresolved.
4. Add or refresh a compact **Continuation Snapshot** near the top of the session containing at least:
   - `Status: CHECKPOINTED` for normal near-term continuation, or `Status: PARKED` when the user explicitly defers/deprioritizes the session;
   - `Activation gate: ...` when one exists, otherwise `NONE`;
   - the latest Chat Segment number;
   - accepted/provisional `D-*` and/or `TD-*` IDs from the persisted work;
   - the exact next question / resume point;
   - deferred branches or finalization notes needed for continuity.
5. Treat the Continuation Snapshot as navigation/handoff metadata, not a competing source of truth. Detailed accepted product behavior remains owned by `design/decisions.md`; implementation/architecture choices remain owned by `design/technical-decisions.md`; detailed reasoning remains owned by the session body.
6. Update `README.md` navigation/current state so status, recommendation class, and resume target are clear. `CHECKPOINTED` sessions rank ahead of normal planned work; `PARKED` sessions rank behind eligible planned work. Neither is auto-selected in a fresh chat.
7. Do **not** perform full Design Session finalization merely because a checkpoint/park was requested: do not mark the session completed, do not regenerate canonical PRD/SPEC, do not run a historical edge-case consolidation, and do not create speculative follow-up sessions unless separately requested or required to preserve already-settled truth. An explicitly authorized `temporary/SPEC.draft.md` may be created/updated under its bounded exception without claiming canonical SPEC completion.
8. Increment the workspace version. Increment the protocol version only if this protocol changed.
9. Preserve unrelated files unchanged, validate the workspace, create the next deterministic complete Workspace ZIP, and return it to the user.

A `CHECKPOINTED` or `PARKED` session is therefore a durable mid-session handoff between Chat Segments, not a completed-session boundary. `PARKED` additionally communicates roadmap deferral. Resuming a `PARKED` session and later issuing `Checkpoint` promotes its persisted continuation state back to `CHECKPOINTED`; issuing `Park` keeps it deprioritized.

### Finish a Design Session

When a design session is complete:

1. Update the current chat-selected session file, mark it `COMPLETE`, and remove/close any obsolete `CHECKPOINTED` / `PARKED` continuation marker now that the conceptual session is complete.
2. Classify newly settled conclusions and write them to the correct ledger: product/behavior decisions to `design/decisions.md` as stable `D-*`; implementation/architecture decisions to `design/technical-decisions.md` as stable `TD-*`. In FAST, surfaced `AUTO` conclusions not overridden before finalization count as settled under the user's bounded delegation; other decision-bearing leaves still require the disposition defined by their classification. A Technical Decision may never override accepted product behavior.
3. Add new follow-up session files only when the branch is important enough to deserve its own chat.
4. Update `output/edge-cases.md` incrementally from the completed session and newly changed/accepted decisions. Keep it scenario-oriented and link to the owning stable decision ID, PRD section, or SPEC section instead of duplicating implementation detail.
5. Review only `concepts/` docs materially affected by the finalized canonical changes. Update or remove any concept known to contradict current canonical truth; known-stale developer guidance is a blocking finalization defect.
6. Update `README.md` navigation/current state:
   - record the last completed session,
   - update completed/open sessions,
   - suggest the next useful session(s),
   - avoid restating the detailed decision set.
7. Increment the workspace version for the new canonical workspace revision. Increment the protocol version only if this protocol changed.
8. Preserve unrelated files unchanged.
9. Validate the complete revision, create and verify one deterministic complete Workspace ZIP for the finalized Workspace Revision, and return it to the user.

A full historical edge-case backfill is **not** required after every normal design session. Perform a complete scan of completed sessions and accepted decisions when running a maintenance/integrity audit, before major PRD/SPEC generation, for a release checkpoint, or when inconsistency is suspected.

### Finish Maintenance / Audit Work

When maintenance changes the canonical workspace:

1. Preserve accepted product/design semantics unless explicitly reopened.
2. Apply only the structural/procedural/status/link changes justified by the audit.
3. Classify every genuine unresolved finding before disposition:
   - if accepted canonical truth already determines the answer, repair it rather than creating design work;
   - if it is ordinary technical freedom already delegated to the SPEC, leave it for technical design;
   - if it is an accepted limitation/safe rough edge, document it as such;
   - only a real missing/conflicting product/design decision requiring decision-making authority proceeds to the selected disposition submode.
4. In **Standard Mode**, prepare focused future design session(s) for those genuine unresolved decisions and keep them out of accepted truth until discussed.
5. In **Handoff Mode**, do not prepare future design sessions for those findings. Create/update stable `OD-NNN` entries in `design/OPEN-DECISIONS.md`, including at least status, impact, blocking flag, problem/conflict, accepted constraints, required decision, and affected areas.
6. Run an integrity check appropriate to the scope; for broad audits, scan all completed sessions, `D-*` and `TD-*` IDs/anchors/statuses/supersession links, Open Questions, Open Decisions, edge cases, cross-links, versions, temporary-spec status, and open-session lifecycle/gate status.
7. Update `README.md` current state without turning it into a changelog or decision summary.
8. Increment the workspace version for the new canonical revision.
9. Increment the protocol version if `WORKSPACE-PROTOCOL.md` changed.
10. Validate the new revision, create and verify the next deterministic complete Workspace ZIP, and return it to the user. Create a Design Package only when `Package` is explicitly requested.

For **Audit** without write/apply permission, perform the same classification and disposition reasoning but keep the result in the audit report: Standard Mode prepares proposed session slots; Handoff Mode prepares proposed `OD-NNN` records. Do not mutate canonical files merely because a submode was selected.

## Implementation Handoff Boundary

When a project has an accepted implementation-handoff contract, ordinary implementation handoff uses the **Portable Implementation Handoff / Portable Implementation Package** rather than treating the fixed nine-file Design Package as the implementation package. The Design Package remains a compact design-only projection for review/sharing and its membership does not change.

A Portable Implementation Package carries two complete pinned framework installations: DWF under `design/.framework/` and DSF under `delivery/.framework/`. Framework payloads are installed dependencies and immutable within one package lineage. Project-owned design truth is exported as a bounded `design/` implementation projection rather than a clone of the whole Design Workspace; historical Design Sessions, collaboration/process state, and Workspace Protocol machinery are excluded from the normal implementation handoff. The project Delivery Definition remains under `delivery/` beside the pinned DSF release.

The package root README introduces only a small amount of framework vocabulary and explicitly recommends the standard zero-context bootstrap path: root README → DWF public consumer contract → DSF public consumer contract → project `design/` map → Delivery Agent Guide → RULES → Agent PRD → Agent SPEC → Repository Orientation → Roadmap. Framework public consumer contracts live at each `.framework/README.md`; deeper internals remain progressively discoverable but are not prerequisites for ordinary consumption. DWF owns the fixed, versioned workspace-to-package projection mapping: workspace `design/decisions.md` maps to package `design/decisions/product.md`, workspace `design/technical-decisions.md` maps to package `design/decisions/technical.md`, and project context, output, and Concept trees preserve their relative shapes beneath package `design/`. The mapping is framework behavior, not per-package configuration.

After bootstrap, Phase work should load the target Phase's authoritative governing design references plus its supporting Concept references. Concepts remain derived/non-authoritative deep dives even when Delivery recommends them. Human PRD/SPEC remain comprehension/review projections, not competing contract authority.

DWF owns the framework-level implementation-package preparation capability in `skills/prepare-implementation-package/SKILL.md`. The skill may use scripts internally without creating a user-facing packaging CLI. Deterministic package integrity validation is mandatory; a genuinely isolated Fresh Implementation Agent evaluation is strongly recommended but optional when the environment cannot spawn a clean Agent/context. Do not simulate Layer 2 by asking the packaging Agent to forget its current context.

Implementation-time Design Gaps follow the accepted package-local authority/amendment path: stop only affected work, obtain explicit human resolution through the Main Agent, update actual project-owned canonical owners, reconcile affected Delivery truth, append immutable `AM-*` provenance with exact predecessor reconstruction material and before/after digests, update package identity, reconcile existing implementation, and resume. Ordinary Package Amendments never modify either `.framework/` payload. Framework upgrades require package rematerialization into a new lineage rather than an Amendment.

Open Questions/Open Decisions remain in the full workspace. When one materially affects implementation, the Agent PRD/SPEC must reference its stable `OQ-*` / `OD-*` ID so the package cannot silently present unresolved behavior as settled.

## File Responsibilities

### `README.md`

Navigation and current state only. It is an index, not the detailed home of decisions.

Allowed repetition is intentionally small: workspace/protocol versions, completed/open session navigation, recommended sequence, parked/checkpointed/gated summaries, current temporary-implementation notice, and pointers to owning files. Session files own durable status/Activation Gates; README owns navigation priority/order. Do not maintain a second detailed design summary here.

### `project-context/RULES.md`

Canonical owner for mandatory **project-specific engineering and delivery rules**. Every Agent must read and enforce it during Workspace Orientation and before substantive project reasoning. Rules use stable `RULE-NNN` IDs and explicit anchors. They constrain how changes are proposed; they never override accepted product behavior, correctness, security, legal obligations, or other explicit requirements.

Do not duplicate rule text into `project-context/context.md`, PRD, SPEC, or sessions. Those files may reference `RULE-*` IDs.

### `project-context/context.md`

Durable product/domain facts, goals, environment information, and constraints that are useful across many sessions and exist independently of brainstorming choices.

**Ownership test:** if a statement became true because the workspace accepted a product/behavior choice, its canonical home is `design/decisions.md`; if it became true because an implementation/architecture mechanism was chosen, its canonical home is `design/technical-decisions.md`. Neither belongs in `project-context/context.md`. Context may point to the owning ledger but should not restate evolving accepted choices.

### `project-context/GLOSSARY.md`

Canonical owner for stable recurring Design Workspace Framework and project terminology, canonical names/casing, and concise definitions. It is a communication aid, not a requirements source.

A glossary entry should stay short and, when behavior is relevant, point to the owning stable decision/PRD/SPEC section rather than restating the full rule. Terms may begin as session-level Working Terminology and are promoted only after their meaning is stable and broadly useful.

Do not use the glossary for unresolved definitions, one-off implementation-local identifiers, ordinary variable names, or behavior/mechanisms that belong in `design/decisions.md`, `design/technical-decisions.md`, PRD, or SPEC.

### `project-context/COLLABORATION.md`

Mandatory workspace-local owner for response style, explanation depth, teaching preferences, and learned terminology. It is interaction metadata only: it may shape **how** design work is communicated, but it must never change **what** the product or technical design means.

Current-chat user instructions override this profile. Keep it short and operational. If it tracks learned terms, add a term only after the user explicitly indicates that future explanations are no longer needed; the absence of a term does not require over-explaining ordinary vocabulary.

### `design/decisions.md`

Canonical current accepted design state. Keep entries concise and link each decision to the session where it was made.

Each decision must have a stable ID such as `D-023` and a matching explicit anchor such as `<a id="d-023"></a>`. Internal links should target the stable ID (`design/decisions.md#d-023`) rather than a generated title slug.

Normalize decision metadata directly below each decision heading as a compact bullet block:

```markdown
- Status: Accepted | Superseded
- Source: `sessions/NNN-session-name.md`
- Scope: V1 # optional
- Superseded by: D-NNN # optional
- Supersedes: ... # optional
- Note: ... # optional
```

Keep `Status` machine-simple. Put partial supersession, scope, extension, or provenance detail in the optional metadata fields rather than embedding it in the status value.

When a decision is superseded, preserve the historical entry and record supersession explicitly instead of deleting or silently rewriting history. Product decisions use only the `D-*` namespace; never supersede a `D-*` by pretending a `TD-*` can override it.

### `design/technical-decisions.md`

Canonical current state and history for implementation/architecture choices. Technical Decisions are downstream of `project-context/context.md` + accepted `D-*` + `output/agent/PRD.md` and may never weaken, reinterpret away, or override those product constraints.

Use the classification test: **could this implementation mechanism change without changing observable PRD behavior?** If yes, it normally belongs here; if no, it normally belongs in `design/decisions.md`.

Each Technical Decision has a stable ID/anchor such as `TD-001` / `<a id="td-001"></a>` and a machine-simple status:

- `PROVISIONAL` — explicitly approved for a bounded temporary implementation slice, but not yet reconciled into the complete architecture. It may authorize implementation only when an explicitly scoped `temporary/SPEC.draft.md` references it. It must be reviewed during canonical SPEC completion.
- `ACCEPTED` — canonical technical architecture. Final `output/agent/SPEC.md` may rely on it normally.
- `SUPERSEDED` — historical Technical Decision replaced by another `TD-*`; preserve the old entry and link to its replacement.

Normalize metadata directly below each heading:

```markdown
<a id="td-001"></a>

## TD-001 — Short title

- Status: PROVISIONAL | ACCEPTED | SUPERSEDED
- Source: `sessions/NNN-session-name.md`
- Related product decisions: D-NNN, ...
- Scope: ... # optional
- Superseded by: TD-NNN # optional
- Supersedes: TD-NNN # optional
- Note: ... # optional

Decision text...
```

Keep IDs stable and never reuse a retired number. When a Technical Decision is superseded, preserve its historical entry and add explicit `Superseded by` / `Supersedes` metadata rather than deleting or silently rewriting history. A later product decision may force technical redesign, but the replacement mechanism is still recorded as a new `TD-*`; no `TD-*` supersedes a `D-*`.

Do not create a separate `technical-decisions.draft.md`. Session files own discussion provenance; this ledger owns current technical decision state/history.

### `design/OPEN-QUESTIONS.md`

Canonical owner for unresolved **factual questions** that require an authoritative answer from a teammate, stakeholder, repository/domain investigation, or another external source before the design can rely on the fact. It is deliberately separate from `design/OPEN-DECISIONS.md`: an Open Question asks **what is true**; an Open Decision asks **what should we choose**.

Each Open Question uses a stable identifier such as `OQ-001` and records at least:

```markdown
## OQ-001 — Short title

- Status: OPEN | ANSWERED
- Asked of / Source: ...
- Related decisions: D-NNN, ...
- Blocking: YES | NO

### Exact Question

...

### Why It Matters

...

### Answer

Pending.
```

Preserve the user's/team-facing question verbatim under **Exact Question** when the wording itself is intended for later use. Do not guess the answer. When an authoritative answer arrives, mark the entry `ANSWERED`, record the answer/source, then promote the resulting durable fact into `project-context/context.md` if appropriate and reopen/update accepted design decisions only when the new fact actually requires it.

Do not use `design/OPEN-QUESTIONS.md` for ordinary implementation choices, speculative enhancements, or design choices that require authority. Concrete implementation/architecture choices belong in technical design and, once explicitly settled, `design/technical-decisions.md`; product/design authority questions follow the normal session / `design/OPEN-DECISIONS.md` rules.

### `design/OPEN-DECISIONS.md`

Canonical owner for genuine unresolved product/design decisions intentionally delegated by **Handoff Mode**. It must remain high-signal and must not become a general implementation TODO list.

Each Open Decision uses a stable identifier such as `OD-003` and records at least:

```markdown
## OD-003 — Short title

- Status: OPEN | RESOLVED
- Impact: PRD | SPEC | BOTH
- Blocking: YES | NO
- Related decisions: D-NNN, ...

### Problem / Conflict

...

### Accepted Constraints

...

### Decision Required

...

### Affected Areas

...
```

Use `Blocking: YES` only when the affected behavior cannot be implemented safely/correctly without choosing an answer. `Blocking: NO` means implementation may proceed elsewhere and the developer can resolve the item when reaching the affected area.

Do not create an Open Decision for an ordinary technical choice belonging to `design/technical-decisions.md` / SPEC, a speculative enhancement, a deterministic document defect, or an accepted limitation. If an Open Decision is later resolved inside this Design Workspace, promote the accepted result into the appropriate canonical owner (normally `design/decisions.md`, PRD, and/or SPEC) and mark the `OD-NNN` entry `RESOLVED` with references rather than silently deleting it.

### `sessions/*.md`

One focused decision area per file.

Use:

```markdown
# Goal

# Relevant Context

# Questions

# Decisions

# Assumptions

# New Gaps Discovered

# Follow-up Sessions
```

A session may be exploratory and end without a decision.

Completed sessions are **historical provenance**: they preserve what was discussed, assumed, and decided at that time. They do not need to be continuously rewritten to match later decisions. If later truth makes a passage dangerously misleading, add a concise supersession/reference note rather than rewriting the historical discussion. `design/decisions.md` remains the current-truth layer.

Open/prepared Design Sessions use the durable lifecycle states `PLANNED`, `CHECKPOINTED`, `PARKED`, or `COMPLETE`. `ACTIVE` is chat-local and must not be persisted as session status. A `PLANNED` session may expose a compact `Session State` near the top.

For an incomplete Design Session that spans multiple chats, the same session file may contain a compact **Continuation Snapshot** near the top. The snapshot exists only to make Chat Segment handoff deterministic: it records `CHECKPOINTED` or `PARKED` status, any Activation Gate, accepted/provisional `D-*` and/or `TD-*` IDs, the next question, and deferred/finalization notes. It must not duplicate full decision text or become a second canonical current-state layer.

The session file owns its durable status and Activation Gate. `README.md` owns current navigation/recommendation ordering and may summarize those fields without becoming a second lifecycle source of truth.

A conceptual Design Session may span any number of Chat Segments; do not create numbered `part-*` session files merely because the AI chat changed.

### `concepts/`

Derived developer deep-dives for substantial subsystems/components. Concepts optimize implementation understanding; they are **not** another source of product or technical truth. Canonical behavior remains owned by `D-*`, `TD-*`, `EC-*`, project rules, and the validated Agent PRD/SPEC. If a concept conflicts with a canonical owner, the canonical owner wins.

Use this qualification test before creating a concept:

> Would a developer implementing, debugging, or reviewing this part materially benefit from one coherent place that connects several canonical decisions/contracts into one subsystem mental model?

Do not create concept files for isolated fields, endpoints, tables, constants, or single decisions. Prefer organic growth: one directory per substantial concept, starting with one `README.md`; split only when real content size/complexity needs multiple focused files. Do not create empty concept directories as placeholders.

Each concept must:

- declare near the top that it is derived/non-authoritative;
- include a **Quick reload** section of roughly 3–6 bullets for the 60–90 second mental-refresh use case;
- state responsibilities and non-responsibilities clearly enough to avoid absorbing neighboring systems;
- identify its principal canonical dependencies under **Canonical references**;
- link to stable `D-*`, `TD-*`, `EC-*`, rules, glossary, and Agent SPEC owners rather than copying ledger bodies;
- label conceptual interfaces, TypeScript, transaction sketches, and state-machine examples as explanatory unless a canonical owner mandates the exact shape; and
- preserve every implementation-required invariant in the Agent SPEC/canonical owner rather than making the concept the only location where the invariant exists.

A practical concept shape is: Quick reload; what/why; responsibilities/non-responsibilities; core model/state; lifecycle/flows; conceptual implementation model where useful; realistic happy/failure/conflict walkthroughs; relationships/traps; canonical references. Omit sections that add no value.

Do **not** maintain a separate `for_dummies/` hierarchy. The Quick reload section inside each substantial concept owns the fast-reload use case.

Concept maintenance is impact-based. When a referenced `D-*`, `TD-*`, `EC-*`, rule, glossary meaning, or Agent SPEC contract materially changes, review the affected concept in the same revision that publishes changed developer guidance. Pure wording/layout changes do not force semantic rewrites. A concept may lag while a working revision is still in progress, but a concept known to contradict current canonical truth is a blocking integrity defect at `Finalize`: update or remove it before publishing the new Workspace Revision.

Concepts are projections, not history ledgers. Edit, rename, or delete them normally; do not create a superseded-concept history system. Historical rationale remains in sessions and canonical decision ledgers/Git revisions. `concepts/README.md` indexes current available concepts and may list qualified future concept candidates without creating empty files.

Recommended reading path when the full Workspace is available:

```text
Mandatory contract
  -> project-context/RULES.md
  -> output/agent/PRD.md
  -> output/agent/SPEC.md

Complex subsystem deep-dive
  -> concepts/<concept>/README.md

Exact provenance / disputed edge
  -> D-* / TD-* / EC-* / glossary owner

Easier whole-system orientation
  -> output/human/PRD.md + output/human/SPEC.md
```

### `skills/`

Reusable workspace methods and capabilities. Skills may change how a concept is explained, investigated, transformed, or packaged, but they do not create product/design decisions by themselves unless an explicit design workflow separately authorizes such decisions.

Two forms are supported:

- **simple skill:** `skills/*.md`;
- **modular Agent Skill:** `skills/<skill-name>/SKILL.md`, optionally accompanied by `references/`, `scripts/`, `assets/`, and eval resources.

For a modular skill, treat `SKILL.md` as the workflow/orchestration entrypoint and use progressive disclosure: load supporting resources only when the skill directs the current stage to use them. Do not preload every skill/reference during normal Workspace Orientation.

When an explicit workspace command names a skill-backed capability, that command determines invocation. Otherwise, when a user's natural-language request clearly matches a skill's description/trigger, invoke the matching skill while preserving the Workspace Protocol's source-of-truth and write-permission boundaries.

`skills/creating-interactive-technical-courses/SKILL.md` owns the reusable course-generation workflow behind the `MiniCourse` command.

### `artifacts/mini-courses/`

Optional persisted Mini-Course Source Packages created only when `MiniCourse --save` (or an equivalent explicit persistence request) authorizes a workspace write. These ZIPs are derived explanatory artifacts, not design truth.

A saved ZIP must record the source Workspace Revision inside its bundled `course-brief.json`. Its presence in a later Workspace Revision means only that the artifact is durably stored and integrity-tracked; it does not make the course authoritative over `design/decisions.md`, PRD, `design/technical-decisions.md`, SPEC, Open Questions, or Open Decisions.

Do not persist compiled course HTML by default. Do not use `output/` for MiniCourse artifacts.

### `output/agent/PRD.md`

The canonical Agent-oriented product-requirement projection. It is generated from `project-context/context.md` plus accepted `D-*` truth, optimized for exactness and low inference. It is not a replacement for `design/decisions.md`; important product choices remain first-class `D-*` entities.

### `output/agent/SPEC.md`

The canonical Agent-oriented implementation projection. It is downstream of project context/rules, accepted `D-*`, Agent PRD, and accepted `TD-*`. Generate and validate the Agent PRD/SPEC **before** deriving Human versions. Important non-trivial sections should carry compact traceability metadata such as `Sources`, `Covers`, `Governed by`, and `Contract` where useful.

The Agent SPEC should minimize avoidable inference for implementation Agents: exact invariants, state transitions, required data shapes, responsibility boundaries, edge conditions, and small contract-defining code/examples should remain explicit when they materially reduce guesswork. Architectural black-box contracts are normative; incidental illustrative signature details remain adjustable unless explicitly marked normative. Richer rationale, lifecycle explanation, realistic walkthroughs, state-machine sketches, and conceptual interfaces may live in `concepts/` when a deep-dive exists, but no required invariant may exist only there.

### `output/human/PRD.md` and `output/human/SPEC.md`

Derived human-oriented projections of the **validated Agent pair**. They optimize transfer of understanding: direct language, concrete actors, cause/effect, compact flows, examples, and TypeScript where useful. Human documents may simplify representation but never behavior. They are not independently authored truth. If Human and Agent projections disagree, the Agent/decision truth wins and the Human projection is regenerated.

Treat roughly 25–50% of a developer's productive daily cognitive budget as a qualitative density target for the human pair, not an SLA.

### `output/edge-cases.md`

Catalog of explicitly considered scenarios. Every durable edge case uses a stable `EC-NNN` ID and anchor, with compact metadata linking to contributing `D-*`, `TD-*`, `RULE-*`, or other durable entities. Edge cases do not own product or technical behavior; they point to the canonical owners.

### Human/Agent projection generation order

When a design change requires regenerated outputs:

1. settle/update canonical `D-*` / `TD-*` entities;
2. generate/update Agent PRD;
3. generate/update Agent SPEC;
4. validate the Agent pair against canonical decisions, rules, open-state constraints, and relevant edge cases;
5. derive Human PRD/SPEC from the validated Agent pair;
6. validate that Human simplification did not change behavior;
7. review only concept docs whose declared dependencies or explained contracts were materially affected, updating/removing any known-stale guidance.

Do not independently design inside Human or Concept projections.

### Traceability model

Stable IDs belong to durable semantic entities, not arbitrary prose. Existing namespaces remain (`D-*`, `TD-*`, `OQ-*`, `OD-*`, `AC-*`) and project rules/edge cases add `RULE-*` and `EC-*`. Keep IDs stable, anchored, searchable, and never reused.

Derived PRD/SPEC headings remain semantic presentation structure rather than acquiring global numeric IDs. Important Agent sections reference the durable entities that justify them. Maintain forward references toward authority; do **not** hand-maintain backlink lists because reverse relationships are discoverable by stable-ID search.

### `temporary/SPEC.draft.md`

An optional **Temporary Partial Implementation Specification** that exists only when the user explicitly authorizes a bounded implementation exception before the full canonical architecture is complete. It must not be created merely because implementation would be convenient.

When present, it:

- is intentionally incomplete and lists its exact implementation scope and exclusions;
- references explicit `PROVISIONAL` `TD-*` entries that authorize only that bounded slice;
- never claims the overall synchronization architecture or canonical `output/agent/SPEC.md` is complete;
- cannot override `D-*`, PRD requirements, accepted `TD-*`, or stronger canonical constraints;
- cannot silently answer, close, or work around `OQ-*` / `OD-*`;
- must avoid pulling unresolved architecture into the temporary implementation slice;
- must eventually be reconciled during canonical technical design; and
- should be removed or archived after reconciliation is complete.

While this exception is active, `README.md` may carry a concise **navigation-only** notice pointing developers to it. Do not put the temporary implementation state in `project-context/context.md`. The temporary SPEC supplements rather than replaces `output/agent/SPEC.md`.

#### Temporary Implementation Slice workflow

A **Temporary Implementation Slice** is a first-class escape hatch for long-running feature design when the team needs safe implementation work before the full architecture is complete. It is intentionally narrow and reversible.

1. The user must explicitly authorize the temporary slice and its implementation lane/scope.
2. Reuse the existing Design Session that canonically owns the relevant technical questions when practical; do not create a duplicate session merely because the temporary slice occurs in another chat.
3. Read the governing `D-*` / PRD constraints and discuss technical choices one meaningful question at a time. Do not turn unresolved `OQ-*` / `OD-*` items into implementation tasks or silently decide unrelated architecture.
4. Only explicitly accepted slice decisions become `PROVISIONAL` `TD-*`.
5. After the bounded TD set is accepted, create/update `temporary/SPEC.draft.md` with enough concrete detail to implement only that slice. Canonical `output/agent/SPEC.md` remains incomplete unless the full technical design is actually complete.
6. Persist the owning Design Session with a Continuation Snapshot. If the slice deliberately bypassed the normal roadmap and the broader session should not be next, default to `PARKED`; use `CHECKPOINTED` only when near-term continuation of that same session is intended.
7. `README.md` must point to the temporary spec for implementers and separately preserve the normal design roadmap. The existence of a temporary spec must not make its owning parked session the automatic next design recommendation.
8. Implementation authorized by the temporary spec does not promote `PROVISIONAL` TDs to permanent architecture. During eventual canonical SPEC completion, review every provisional TD and promote/reconcile it to `ACCEPTED` or explicitly `SUPERSEDED`.
9. After reconciliation, remove or archive the temporary spec and clear its README navigation notice.

This capability may be used again later when another genuinely safe bounded slice is needed, but each use requires explicit user authorization and must preserve the same scope discipline.

## Knowledge Ownership and Duplication

Use these rules when the same topic appears in more than one place:

1. **Owning file wins.** A navigation summary, concept, or historical session never overrides its canonical owner.
2. **Detailed accepted product/observable behavior belongs in `design/decisions.md` (`D-*`)** during brainstorming and flows into PRD.
3. **Detailed implementation/architecture choices belong in `design/technical-decisions.md` (`TD-*`)** and flow into SPEC. A `TD-*` cannot override `D-*` / PRD.
4. **Stable recurring project terminology belongs in `project-context/GLOSSARY.md`.** The glossary owns names/definitions only and must link to, not duplicate, behavior/mechanisms owned by the decision ledgers, PRD, or SPEC.
5. **Unresolved factual questions awaiting authoritative external/domain answers belong in `design/OPEN-QUESTIONS.md`.** They are not design decisions and must not be guessed.
6. **Genuine intentionally delegated unresolved product behavior belongs in `design/OPEN-DECISIONS.md`** only when Handoff Mode selected that disposition.
7. **Durable independent facts belong in `project-context/context.md`.**
8. **Mandatory project-specific engineering/delivery constraints belong in `project-context/RULES.md` as stable `RULE-*` entities.**
9. **Explicitly considered edge-case scenarios belong in `output/edge-cases.md` as stable `EC-*` entities that link to their canonical behavior owners.**
10. **Reasoning/provenance belongs in `sessions/`.** A single session may produce `D-*`, `TD-*`, both, or neither depending on what was actually decided.
11. **Derived subsystem implementation understanding belongs in `concepts/`.** Concepts transform/link canonical truth and may carry richer explanatory code/flows, but never own required behavior or architecture.
12. **README repetition is navigational only.** Prefer links over copied decision bullets; temporary implementation state may appear only as a navigation notice.
13. **`temporary/SPEC.draft.md` is an explicitly bounded exception, not another canonical current-state layer.** It may operationalize referenced provisional TDs only within its stated scope.
14. Do not solve duplication by creating another summary/current-state file; in particular, do not create `technical-decisions.draft.md` or a separate `for_dummies/` truth layer.

## Framework and Project Terminology / Glossary

Use `project-context/GLOSSARY.md` to stabilize vocabulary that recurs across sessions, decisions, PRD/SPEC, or implementation discussions. The glossary is a naming/definition aid, not another requirements source.

- A new term may begin as **Working Terminology** inside the current chat-selected session while its meaning is still being explored.
- Promote a term to `project-context/GLOSSARY.md` when it becomes stable and is reused across multiple files/sessions, or when inconsistent wording would create real ambiguity.
- Keep glossary entries concise: canonical name/casing, one short meaning, and links to the `D-*`, `TD-*`, PRD, or SPEC sections that own behavior/mechanism. Do not copy full rules into the glossary.
- Do not promote one-off implementation-local identifiers merely because they appear once; prefer terms that help the project communicate consistently.
- If an accepted design change materially changes a glossary term's meaning, update the glossary in the same canonical workspace revision. Do not silently redefine the same term differently in a later session.
- During normal Design Session finalization, review any session **Working Terminology** and promote only terms that meet the stability/reuse threshold.

## Decision Rules

Accepted `D-*` and `TD-*` decisions are stable by default. `PROVISIONAL` TDs are stable within their authorized temporary scope but remain mandatory review items for canonical SPEC completion.

Classify before assigning an ID:

- If changing the choice would change observable PRD behavior, it is normally a product/design decision -> `D-*`.
- If the mechanism could change while preserving observable PRD behavior, it is normally an implementation/architecture decision -> `TD-*`.
- A Design Session may produce either type; never force architecture into `D-*` merely because it was discussed in a session, and never hide product behavior changes in `TD-*`.

Reopen a decision only when:

- the user explicitly requests it;
- new information contradicts it;
- another accepted decision makes it impossible.

When reopening or replacing one, record the reason in the relevant session and update the owning ledger rather than silently replacing history. Supersession stays within its namespace: old `D-*` or `TD-*` entries remain present with explicit replacement links. Never renumber, recycle, or silently repurpose a stable ID.

A Technical Decision is always subordinate to product truth. If a `TD-*` conflicts with an accepted `D-*` or PRD guarantee, the technical choice is invalid and must be revised/superseded unless the product decision is separately and explicitly reopened.

## Branching Rule

During **Design Session Mode**, when a new important question emerges:

1. First classify it. If it is an unresolved existing-system/domain fact that requires an authoritative external answer rather than a design choice, capture it in `design/OPEN-QUESTIONS.md` and do not guess it.
2. If it changes observable product behavior, treat it as product/design work (`D-*` when settled). If it only selects implementation/architecture while preserving PRD behavior, treat it as technical design (`TD-*` when settled/provisionally approved).
3. Determine whether it is a descendant of the current conceptual branch or a genuinely different conceptual branch.
4. Under **NORMAL**, capture important newly discovered branches under `New Gaps Discovered`; if dedicated discussion is warranted, create/suggest a future session, then return to the current session goal.
5. Under **FAST**, newly exposed descendant leaves may remain in the same Design Session and enter a later Frontier Wave only when they stay inside the current conceptual branch. A genuinely different conceptual branch is classified `DEFER`, captured as future work, and is not traversed.

FAST therefore permits bounded breadth-first traversal **within** the current branch; it does not authorize recursive exploration of the whole project design tree. A long Design Session may still be checkpointed across multiple Chat Segments only when the user explicitly requests it.

During **Maintenance / Audit Mode**, do not automatically reuse this future-session disposition. Genuine unresolved decision findings follow the explicitly selected submode: Standard → prepare future focused session(s); Handoff → `design/OPEN-DECISIONS.md`.

## Design Style

Prefer:

- simple over clever;
- boring over novel;
- deep modules with small interfaces;
- explicit authority and ownership;
- isolated domain responsibilities;
- recoverable behavior;
- complexity only when justified by a real requirement.

Act as an engineering colleague rather than a passive confirmer. Evaluate proposals independently against accepted product invariants, team capability, delivery speed, and system simplicity. Push back clearly when a requested direction creates disproportionate complexity, weakens correctness, or conflicts with earlier decisions; do not contort the design merely to satisfy the user's latest preference. When a new statement unexpectedly contradicts a just-established invariant, surface the contradiction instead of immediately rationalizing it.

Default tradeoff priority is: happy-path correctness, simplicity/understandability, delivery speed, recoverability, then UX elegance for rare edge cases. Rare edge cases may be handled roughly or remain unresolved when the failure is safe/recoverable and a polished solution would add disproportionate complexity.

### Current-State Documentation Rule

Current-state artifacts should describe the **current contract directly**. When revising canonical PRD/SPEC, current decisions, Concepts, rules, or implementation guidance, remove obsolete transition narrative unless the history itself is necessary to understand migration, compatibility, supersession, audit, or provenance. Prefer statements such as "In V1, the Sync Mode control surface is the Dashboard" over prose that narrates what the design used to be before reaching the current rule.

Historical before/after narrative belongs in artifacts whose purpose includes provenance, such as Design Session discussion, explicit supersession metadata, package Amendments/changelogs, or migration notes. Do not make implementation-facing/current-state documentation carry historical terminology merely because the design evolved through earlier alternatives.

## Chat Interaction

Keep interaction concise, but follow the selected Design Pace rather than applying one cadence to every Design Session. Always use the mandatory `project-context/COLLABORATION.md` profile for workspace-local communication preferences; current-chat user instructions always override it.

Under **NORMAL**:

- Discuss one important concept/question at a time.
- Give a recommendation and the main tradeoff.
- Let the user react before expanding into another branch.
- Do not dump the entire open decision tree unless asked.
- When a low-level local detail is genuinely straightforward, has no meaningful competing tradeoff, and does not deserve a stable decision ID, the agent may choose the standard/simple option and surface it briefly. Creating or changing a `D-*` or `TD-*` requires explicit user acceptance.

Under **FAST**:

- Use **Frontier Wave Traversal** from `skills/frontier-wave-traversal.md`; speed comes primarily from batching related leaves, not from lowering reasoning quality.
- A Fast Decision Packet contains at most **5 leaves**. If one frontier requires more than 5 leaves to be surfaced/processed, split it into multiple packets from the **same wave** and finish that wave before advancing to descendants.
- `AUTO` may settle only choices that satisfy the bounded delegation criteria; surface each AUTO decision and its reason immediately enough for the user to override it before persistence.
- `PACKET` leaves carry a recommendation/tradeoff and require user disposition, but one user response may explicitly accept/reject/modify several packet leaves together.
- `DEFER` leaves are not guessed or prematurely traversed. Record the reason and continue unaffected siblings when safe.
- `BRAKE` leaves receive NORMAL-style treatment. Apply the brake locally when possible; if the uncertainty affects the branch root or multiple downstream leaves, stop frontier advancement until it is resolved.

If the user says **"Resume"**, use the canonical `Resume` command behavior. In a fresh chat, do not auto-select: present resumable `CHECKPOINTED` sessions before `PARKED` sessions and ask which one to resume unless the user already named the session. Resolve Design Pace after selection unless the same instruction already specified it.

If the user says **"Continue"** without specifying another goal, continue the current chat-selected Design Session using its current Design Pace. If no session is selected in the current chat, perform Workspace Orientation and ask the user to choose rather than automatically selecting from persisted state.

If the user explicitly asks to audit, clean up, review, repair, improve, or reorganize the workspace/protocol/knowledge system, use Maintenance / Audit Mode instead of advancing an open product session. Before substantive maintenance/audit work, require an explicit **Standard** or **Handoff** selection; if omitted, ask which one the user wants. FAST never applies to Maintenance / Audit Mode.

If the user says they do not understand a concept, asks for a realistic case, asks to visualize the process, or requests a step-by-step execution example, use `skills/realistic-case-walkthrough.md`.

## Text and Archive Normalization

Canonical Design Workspace files use these normalization rules:

- Markdown/text is UTF-8 without BOM, Unicode NFC, and LF line endings.
- Every text file ends with exactly one newline.
- No tabs, trailing whitespace, or accidental repeated blank lines.
- Preserve Markdown/code semantics while normalizing; do not reflow prose merely to satisfy a line-length preference.
- Canonical Markdown/text files use UTF-8/LF/NFC normalization before packaging into Workspace ZIPs and Design Packages.
- A published **Workspace Snapshot** contains exactly one version-matching workspace root plus its canonical files; editor/OS junk, obsolete transport-control files, and duplicate nested workspace roots are excluded.
- A published **Design Package** preserves the semantic directory paths and contains exactly the nine files defined by the `Package` command; no extra files are added.
- Snapshot and Package entries are sorted and use deterministic archive metadata so re-exporting identical committed content produces identical bytes.

A broad maintenance/integrity pass should validate these rules together with `D-*` and `TD-*` IDs/anchors/sources/statuses/supersession links, Open Question IDs/status, Open Decision IDs/status/links, internal links/anchors, README/session-file lifecycle, Activation Gate, recommendation order, and temporary-spec status, and stale open-session questions that have already been resolved elsewhere.

## Versioning

Track two numbers in `README.md`:

```text
Workspace version: NNN
Protocol version: NNN
```

- Increment **workspace version** whenever canonical Design Workspace contents change and a new complete **Workspace Revision** is produced, including protocol-only, maintenance, status, link, or design-state changes.
- Increment **protocol version** only when `WORKSPACE-PROTOCOL.md` changes.
- If no canonical file changed, do not create a new workspace revision.
- Never commit two different canonical payload states with the same workspace version.
- `Snapshot` and `Package` are read-only export operations and do not increment workspace version by themselves.

Suggested Workspace ZIP archive/root name:

```text
workspace-vNNN.zip
workspace-vNNN/
```

Suggested Design Package name:

```text
design-package-vNNN.zip
```

The latest complete Workspace ZIP explicitly supplied by the user is canonical for the current chat. The extracted working copy is provisional until a persistence operation produces and returns the next complete Workspace ZIP. A Design Package is a structured design projection and cannot replace the canonical Workspace ZIP.

## Source-of-Truth Priority

Inside a chat, use:

1. explicit current-chat user statements;
2. the current valid Design Workspace extracted from the latest complete Workspace ZIP supplied by the user, using the owning file for the type of information in question;
3. project-level protocol/context;
4. prior chat history.

Within the workspace:

- `WORKSPACE-PROTOCOL.md` owns concrete procedure;
- `project-context/context.md` owns durable independent facts/constraints;
- `project-context/RULES.md` owns mandatory project-specific engineering/delivery constraints and is read before substantive reasoning;
- `project-context/GLOSSARY.md` owns stable recurring terminology definitions/casing but never overrides behavior;
- `project-context/COLLABORATION.md` is mandatory, owns workspace-local interaction calibration only, and never overrides design truth;
- `design/decisions.md` owns current accepted product/observable-behavior choices (`D-*`);
- `output/agent/PRD.md` consolidates product requirements from accepted product truth;
- `design/technical-decisions.md` owns current implementation/architecture choices (`TD-*`) and is always subordinate to `D-*` / PRD;
- `output/agent/SPEC.md` is the complete canonical technical specification assembled from the product constraints plus canonical technical decisions;
- `temporary/SPEC.draft.md`, when explicitly active, authorizes only its bounded scope from referenced `PROVISIONAL` TDs and never replaces `output/agent/SPEC.md`;
- `design/OPEN-QUESTIONS.md` owns unresolved factual questions awaiting authoritative external/domain answers and never supplies guessed facts;
- `design/OPEN-DECISIONS.md` owns explicitly delegated unresolved product/design choices and never overrides an accepted decision;
- session files own durable lifecycle status/Activation Gates plus reasoning/provenance, not current decision truth; `ACTIVE` remains chat-local only;
- edge cases own scenario summaries, not underlying rules;
- workspace skills own reusable procedures/capabilities only and never override canonical product/technical truth;
- persisted `artifacts/` are derived non-authoritative outputs and never override their recorded source revision;
- README owns navigation/current state and recommended session ordering only.

Never invent missing repository or domain facts.
